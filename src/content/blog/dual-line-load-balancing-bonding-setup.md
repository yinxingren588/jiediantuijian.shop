## 宽带聚合与策略负载均衡的底层运行机制

网络聚合并非将两个物理网卡粗暴地‘焊在一起’，而是通过内核级的调度算法将并发连接分摊到不同出口：

1. **基于会话的负载均衡 (Session-based Load Balancing)**：这是最稳定可靠的方案。单一次 TCP 连接（如单线程下载）只能走其中一条线路，但当你开启多线程下载或同时打开多个网页时，路由器将连接**按 1:1 轮询（Round-Robin）或权重比例（Weighted）**均匀分发至两条宽带，总并发带宽完美叠加！

2. **基于源 IP 散列的粘滞会话 (Sticky Sessions)**：确保同一网站的多次交互请求在短时间内走同一出口，彻底杜绝网银或 ChatGPT 因 IP 瞬间跳变而强制踢下线的风控风险；

3. **多专线跨国多活热备**：两家机场同时跑流量，任何一家遭遇机房切线，健康探测探针在 100 毫秒内自动剔除故障节点，用户完全感知不到断网。

## Clash Verge Rev 策略组配置多机场专线负载均衡实操

### 生产级配置与实操代码

```yaml
# Clash Verge Rev (Mihomo 内核) 双专线负载均衡策略组完整配置
proxy-groups:
  # 1. 定义负载均衡核心组 (采用轮询机制并发叠加带宽)
  - name: "⚖️ 双专线极速聚合-轮询"
    type: load-balance
    strategy: round-robin # 轮询分发，支持 round-robin 或 consistent-hashing
    url: "https://www.google.com/generate_204"
    interval: 30
    proxies:
      - "🇭🇰 主力机场A-深港专线01"
      - "🇭🇰 备用机场B-广港专线01"
      - "🇯🇵 主力机场A-沪日专线01"
      - "🇯🇵 备用机场B-沪日专线01"

  # 2. 针对需要固定 IP 登录的金融与 AI 业务单独配置粘滞策略
  - name: "🤖 敏感业务-固定专线"
    type: fallback
    proxies:
      - "🇭🇰 主力机场A-深港专线01"
      - "🇭🇰 备用机场B-广港专线01"

rules:
  - DOMAIN-SUFFIX,openai.com,🤖 敏感业务-固定专线
  - DOMAIN-SUFFIX,alipay.com,DIRECT
  - MATCH,⚖️ 双专线极速聚合-轮询
```

#### 核心实施要点
1. **选用 round-robin 策略实现大吞吐**：在 `load-balance` 策略组中将 strategy 设为 `round-robin`，利用多线程下载工具（如 IDM 16 线程）拉取大文件，即可观察到两条线路同时跑满千兆带宽。
2. **对 AI 和网银实施粘滞分流**：绝对不能让 ChatGPT 或银行登录走轮询组，务必像上文配置那样单独立一条 `fallback` 固定专线，防止因 IP 瞬间跳变被封号。
3. **两家机场采用异构选型**：两家机场的入口机房和团队必须完全独立，才能真正发挥出双倍容灾的战略价值。

## 双线聚合高频踩坑排除


### 场景 1：下载测速确实翻倍了，但经常遇到某些网站提示‘登录状态已失效请重新登录’
- **底层原因剖析**：该网站开启了严格的 Session IP 绑定，轮询负载均衡导致前后两次请求来自不同机场的出口 IP。
- **针对性解决对策**：在客户端规则集中将该域名加入特定的固定单节点策略组中。


### 场景 2：其中一条宽带断网后，网页加载变卡顿
- **底层原因剖析**：负载均衡策略组的心跳健康检测周期过长（如设为了 300 秒），导致客户端在几分钟内依然不断向死线路发包。
- **针对性解决对策**：将 `interval` 调小至 15~30 秒，确保故障节点在半分钟内被自动移出可用池。
