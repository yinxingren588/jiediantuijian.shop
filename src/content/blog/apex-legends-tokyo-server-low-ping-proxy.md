## Apex 网络状态机与 20Hz Tick 延迟补偿惩罚

Apex Legends 采用基于 Valve Source 引擎魔改的网络架构。其最受争议的技术特征就是**服务器 20Hz 的超低刷新率 (Tick-Rate)**。

在 20Hz 的环境下，服务器每 50 毫秒才对战场上的物理与弹道状态进行一次仲裁广播。
由于刷新率低，游戏引擎对“延迟补偿 (Lag Compensation)”进行了非常极端的倾向性设计：
- 如果你的网络存在**抖动或丢包**，对方客户端在上一个 Tick 命中了你的幽灵残影，即便你在本地屏幕上早已滑铲进入掩体，服务器依然会把你“拉回”掩体外判定击杀（俗称“掩体后暴毙”）。
- 右上角一旦亮起红色的**折线（Jitter 抖动）**或**小红点（Packet Loss 丢包）**，你的跟枪就会严重空弹、吃伤害判定延迟。

要征服高段位日服排位，不仅要 Ping 值低（上海直达东京约 28~35ms，华南直达约 40~50ms），更核心的是必须**0 丢包、0 抖动**。

## 生产级配置与工程落地指南

### 针对 Apex 英雄对局服务器的高性能分流策略

```yaml
# 针对 Apex Legends 日服排位的超低延迟专线策略
proxy-groups:
  - name: "Apex-Tokyo-Dedicated"
    type: fallback
    # 优选针对日本东京机房有原生 BGP 互联的 IPLC 游戏专线
    proxies:
      - "JP-IPLC-Tokyo-Game-01"
      - "JP-IPLC-Tokyo-Game-02"
    url: "http://www.gstatic.com/generate_204"
    interval: 30

rules:
  # EA / Respawn 认证与反作弊心跳
  - DOMAIN-SUFFIX,respawn.com,Apex-Tokyo-Dedicated
  - DOMAIN-SUFFIX,ea.com,Apex-Tokyo-Dedicated
  - DOMAIN-SUFFIX,easy.ac,Apex-Tokyo-Dedicated
  
  # Apex 亚太及东京对战服务器 IP 范围精准覆盖
  - IP-CIDR,161.97.0.0/16,Apex-Tokyo-Dedicated,no-resolve
  - IP-CIDR,185.179.200.0/22,Apex-Tokyo-Dedicated,no-resolve
  - IP-CIDR,209.58.128.0/18,Apex-Tokyo-Dedicated,no-resolve
```

#### 推荐实施执行路线
1. 在代理客户端开启 TUN 模式，确保 Steam 或 EA App 启动的 r5apex.exe 流量全部被接管
2. 在主界面进入数据中心选择列表，手动选择延迟最低且丢包为 0% 的 'Tokyo' 服务器
3. 在游戏内启动参数中加入 +cl_showfps 4 与 +fps_max 190，锁定稳定帧率以降低渲染引擎抖动
4. 保持专线节点连接，在训练场切枪拉靶确认右上角无任何红色警告图标后再开启排位

## 常见疑难故障排查与实战应对

### 场景 1：开局跳伞阶段画面极其卡顿，右上角持续显示红色双向箭头 (Prediction Error)
- **底层成因分析**：物理服务器瞬时负载过载，或者专线节点在此时间段分配了过大的缓冲区导致延迟膨胀。
- **针对性解决方案**：若属于整局所有玩家共同现象，则为 EA 服务器本身问题；若仅个人发生，切换备用东京专线。


### 场景 2：进入对局几分钟后被强行踢回大厅，提示 'Anti-Cheat Error' 或 'Client not responding'
- **底层成因分析**：本地 Easy Anti-Cheat (EAC) 反作弊心跳包被代理规则误拦截或由于节点频繁重拨超时。
- **针对性解决方案**：将 easy.ac 与 eac-cdn 等反作弊域名设为直连或稳定的低延迟专线白名单。


### 场景 3：手动选了东京服，但匹配进去后延迟显示为 120ms，明显到了新加坡服
- **底层成因分析**：匹配大厅在高峰期开启了跨服调度，将部分玩家溢出分配到了东南亚机房。
- **针对性解决方案**：在网络设置中显式限制对局 IP 范围，或在排位人数充足的时间段开对局。
