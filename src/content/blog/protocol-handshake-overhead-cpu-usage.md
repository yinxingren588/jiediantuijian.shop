## 千兆宽带跑不满，竟是路由器 CPU“被烧熟了”？

很多用户满怀期待地将家里的宽带升级到了千兆，也购买了顶级专线机场，但在下载大文件时却发现网速死活卡在 300Mbps。伸手一摸弱电箱里的路由器，机身滚烫，后台 Web 仪表盘显示 CPU 核心利用率持续 100% 满载爆红！

决定终端吞吐上限的，除了物理光纤，还有客户端硬件处理**对称加密算法（Encryption & Decryption）**的算力瓶颈。不同协议与加密套件对 CPU 资源的消耗差异高达数倍。今天我们用真实硬件跑分，教你如何为你的设备选对最省电、最凉爽的协议。

## 硬件指令集分水岭：AES-NI vs ChaCha20 算法机理

1. **AES 算法 (AES-128-GCM / AES-256-GCM)**：国际标准密码算法。在现代 x86-64 架构 CPU（Intel / AMD 电脑及大部分软路由）上，芯片厂商直接在硅晶圆中蚀刻了专门的硬件指令集——**AES-NI**。开启硬件加速后，加解密如同流水线硬件执行，CPU 开销几乎忽略不计；

2. **ChaCha20-Poly1305 算法**：由著名密码学家 Daniel J. Bernstein 设计。它纯粹依靠简单的加法、异或和循环移位（ARX）软件计算，**专门为没有 AES 硬件加速芯片的低性能 ARM 架构设备（如老旧手机、廉价树莓派、入门级智能路由器）量身定制**；

3. **双重加密的灾难**：像旧版 VMess 这样在外层 TLS 内部又包一层 AES 的协议，会导致指令集流水线频繁中断与内存上下文反复切换，算力开销成倍放大。

### 不同硬件平台上 AES 与 ChaCha20 纯算法吞吐跑分对比 (OpenSSL Speed)

| 测试运行硬件平台 | AES-128-GCM (开启硬件加速) | ChaCha20-Poly1305 (纯软件流计算) | 结论与选型黄金法则 |
| :--- | :--- | :--- | :--- |
| Intel N100 软路由 (x86架构带AES-NI) | 极速 3,450 MB/s (轻松跑满万兆) | 良好 720 MB/s (CPU占用率明显升高) | 坚决首选 AES 套件，功耗极低 |

## 根据本地路由器型号科学编排密码套件

### 生产级配置与实操代码

```yaml
# 软路由优化选择：为不同设备指定最优节点密码套件
# 1. 针对 x86 软路由 (Intel/AMD) 选用：
proxies:
  - name: "x86极速专用-AES"
    type: ss
    cipher: "2022-blake3-aes-128-gcm" # 硬件加速跑满

# 2. 针对无 AES 加速的老旧小硬路由选用：
  - name: "老路由救星-ChaCha20"
    type: ss
    cipher: "chacha20-poly1305"
```

#### 核心实施要点
1. **查验路由器 CPU 是否支持 AES-NI**：在 Linux / OpenWrt 终端运行 `cat /proc/cpuinfo | grep aes`，若输出高亮包含 `aes` 则说明支持硬件直加速。
2. **支持 AES-NI 的设备优选 AES**：工控机软路由用户坚决选用基于 AES 的协议套件，发热大幅减少 5~10℃。
3. **无加速的轻量设备坚守 ChaCha20**：百元级未内置加密协处理器的老旧硬路由，果断选择 ChaCha20-Poly1305 以免死机重启。

## CPU 过载导致的吞吐异常排查


### 场景 1：下载大文件时网速爬升到 300M 后突然断流，路由器 Web 界面卡死打不开
- **底层原因剖析**：加解密计算消耗了 100% 的 CPU 周期，导致路由器系统内核调度失去响应，崩溃重启。
- **针对性解决对策**：将代理节点更换为经过轻量化优化的 VLESS 或开启 AES-NI 加速的 Shadowsocks 节点。


### 场景 2：手机连接代理打游戏时机身明显发烫掉电极快
- **底层原因剖析**：选用了复杂的双重嵌套伪装协议，移动端芯片持续高频计算加密报文。
- **针对性解决对策**：切换为轻量级零冗余的 TUIC v5 或原生专线协议。
